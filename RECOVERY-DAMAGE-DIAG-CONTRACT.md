# Bounded read-only damage diagnostic (candidate)

`1.1.8-recovery-interact-diag.1-from-test2` is an independent diagnostic descendant of frozen interaction-v2. It does not repair or reinterpret the failed TEST, authorize combat, or add an execution operation. The original v2 package, failed TEST, formal cold checkpoint, existing owner and94 historical actions remain intact.

## Why new evidence is needed

The first v2 TEST made one read-only observation and zero gameplay POSTs. It had no new native/public record and no active/UNKNOWN entry, but health and position changed after world entry. Saved horizontal Motion was zero both before and after; armor wear, damage_taken and HurtByTimestamp changed. No live DamageSource was recorded. The nearby list was only an8-block living-entity sphere: an empty list cannot exclude projectiles, distant actors or an earlier attacker. Cold NBT and old caches cannot reconstruct the individual cause. In particular HurtByTimestamp can also change while clearing the remembered attacker and is not a proven attack time.

The v2 preTick/input/postTick and input-isolation sources are byte-identical to the preceding executor where relevant; no active/capture means no executor input write. This narrows the evidence, but does not prove the cause was ordinary AI or exclude every transient UI/runtime behavior. The new diagnostic measures rather than guessing.

## Passive event and input evidence only

Use the pinned NeoForge `LivingDamageEvent.Post`, a non-cancellable post-damage event. Observe only the local private integrated-server player on the owning server thread. Record bounded structured source identity, direct/causing entity identity and position when safely readable, original/new/blocked damage, player health/position, server tick/time and the most recently published client-side native owner/active/history-count snapshot with its own sample time. The damage callback does not take the ledger lock; this authority snapshot is explicitly not current-at-damage or atomic with damage. The unchanged94-record journal is independently checked at cold boundaries. Unreadable fields remain explicitly unknown; no unrelated entity census, attacker AI simulation or future-safety proof is added.

Never call a damage setter, cancel, entity interaction, movement/control method, weapon/death-message renderer or lifecycle mutator to obtain diagnostic data. No new AT or Mixin is needed. Existing action admission, callback fencing, release, old profile readers, journal bytes and UNKNOWN semantics remain unchanged. A small pure native metadata accessor may expose owner/active/count without granting authority.

The client records an initial finite input-observation window, including actual forward/strafe/jump state and health/pose. This is not OS keyboard logging or a complete input-callback trace. Client and server observations have separate clocks/threads; they are not an atomic combined snapshot and must not be presented as such. Damage records retain the first32; input samples retain a32-entry ring of changes/20-tick heartbeats, plus separate first/latest summaries. Total client Post samples and nonzero-input count/first occurrence cover the whole finite window; the ring is not a continuous movement recording. Explicit dropped/overflow/window state is reported. The latest summary is separately bounded. A counter overflow is not silently treated as complete history. Diagnostic responses have a separate128KiB bound; the original action64KiB and ledger8MiB limits do not change.

Startup flag `mineclientBridge.recoveryDamageDiagnostics=true` enables this diagnostic and authenticated GET-only `/control/recovery-diagnostics/v1/events`. The tested setup retains `mineclientBridge.recoveryInteractionV2=true` and `mineclientBridge.isolatedInput=true`, but no effect request is authorized in this diagnostic session. It uses the existing loopback credential, never a new credential. The native implementation is memory-only; it must not overwrite ledgers or save diagnostic configuration. An external standalone watcher persists each original HTTP response with status, completeness, byte length, hash and timing. Events cannot be recovered from this memory after process exit; cold files are not represented as an old live cache.

## One short new TEST, not a success loop

After independent source/package review and parent admission, the sole operator copies the protected HP20 formal cold checkpoint to a new explicitly named diagnostic TEST. The failed HP0.533 TEST is retained without rollback. Do not spawn/remove creatures, grant invulnerability, edit health or alter the obstruction to force a result.

Pre-arm the GET-only watcher before launch so no long terminal command is typed while the game is focused. Startup waiting is bounded to60s; the in-world observation window is bounded to12s after its first valid world observation. The watcher must write an atomic close trigger on the first damage record, health loss, unexpected position change, incomplete/invalid transport evidence, or expiration. The operator's separately reviewed normal-window-close procedure consumes that trigger promptly; the watcher itself cannot control the game or POST. Do not wait for model discussion while the player takes damage.

Every raw response is preserved before classification. A complete short window with no event is `not_reproduced`, not proof of future safety and not permission to repeat until an attack occurs. Transport uncertainty is diagnostic incompleteness, not an action UNKNOWN: this session sends zero actions. Original94 action receipts and UNKNOWN rules are untouched. This diagnostic only aims to identify a concrete current injury mechanism and then return the normal task to the parent decision; it is not a new global validation project.
