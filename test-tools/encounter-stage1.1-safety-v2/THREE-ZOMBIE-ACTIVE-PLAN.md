# One controlled three-zombie active case

This is a callable-entry and acceptance plan, not authorization or a live result.
Only the existing sole operator may perform game operations after the parent
confirms the integrated artifact and this exact case. No multiplayer, new access,
credentials, extra writer, old watchdog, attack or chase is involved.

## Scope

One ordinary private singleplayer case: exactly three adult ordinary zombies with
normal AI, on the same forward side of a full-health player, in an already loaded,
flat dry area. Suggested relative spacing is center and approximately one block
left/right at about six blocks initial horizontal separation. The operator must
use actual observed safe geometry and identities, not these suggestions as a
world-edit command. A known clear retreat direction is necessary. No skeleton,
projectile, fourth hostile, block/terrain edit or additional scenario is included.

The purpose is to establish the new three-identity binding, one bounded native
retreat, zero attacks, truthful terminal risk, input release/pause and exact
three-target closeout. A budget/no-route/freshness refusal is a stopped case, not
permission to repeat. No arbitrary number of retries or performance acceptance
threshold is introduced.

## Callable path (no new transport)

Use the existing explicitly supplied PostTrialSafety/operator/queue objects:

- Register with `register_active_case(case_id, entities, observation,
  evidence_ref=..., active_ai_proof=..., authorization_ref=...,
  pause_authorization_ref=..., previous_case_authorization_ref=...,
  encounter_mode='three_zombie_retreat_v1')`.
- Build the ordinary EncounterBinding with the exact ordered three identities,
  exact target inside them, `approach:false`, `shield:false`, and
  `encounter_pause_on_terminal:true`; retain the same immutable action/world/
  player/session/navigation values. No hidden movement/input fields are allowed.
- Call `run_registered_three_zombie_case(safety, binding, trial_name,
  resume_authorization_ref=...)` once. The wrapper uses the existing runner's
  durable dispatch claims and explicit one-resume/one-action path. The sample IDs
  shipped in synthetic tests must never be used for the live request.

The runner does not create enemies, install code, set feature properties, invent
approval references, connect accounts, construct transport or perform cleanup.

## Required observations and stop classifications

- Native admission identifies the new mode, exact ordered scope, zero offense,
  original shared budgets and complete fresh projectile observation.
- At most one original action request. Preserve queue receipt and all native
  running/terminal observations; never resubmit an unknown action under any ID.
- Any live projectile inside the bounded scan causes zero movement at the next
  decision callback and terminal `encounter_projectile_observed_risk_remaining`.
  Do not inject an arrow for this scenario or interpret this as arrow defense.
- Unknown projectile evidence refuses with
  `encounter_projectile_observation_unknown_risk_remaining`; a failed, truncated
  or stale entire scan uses its original `threat_snapshot_*_risk_remaining`.
  No fallback scan or zero-default is permitted. These cases have offline tests;
  if naturally encountered live, save the stop and end the case.
- Any health loss, unsupported/fourth threat, pause/input uncertainty, rescue,
  changed world/player/session, missing proof or unknown action is a stop/report.
  A native unknown pause attempt is not repeated. Read-only reconciliation does
  not become a fresh trial or extra budget.
- Record actual accumulated travel/ticks/wall time, plan/revalidation costs,
  reason, input release and separately observed native pause. Limited three-sample
  clearance success still means three living enemies and risk remains.

## Exact separate closeout

After a known bound released terminal and actual paused-state evidence, the
separately authorized sole operator may perform the existing exact-UUID closeout.
For each of the three originally registered identities, in the same order, retain
one dispatch receipt and a complete observation positively showing that exact
entity dead with health zero. Preserve coordinates/coverage and prior death proof.
Do not use a broad selector; absence is not death. Unknown cleanup must not be
repeated, and stops the remaining cleanup sequence pending operator reconciliation.

`record_operator_closeout` verifies exactly three such proof entries and a matching
final observation with a fresh read. It is read-and-append only. Keep the original
report, safety stop, native terminal and ledger anchors byte-identical. No automatic
next case or ordinary mutation follows. The closeout proves fixture cleanup only,
not combat kills, survival or all P2 objectives.
