# Integrated offline candidate 1.1.7-integrated.1

This is a single newly built Java runtime candidate plus optional source tools. It combines changes relative to the same verified `1.1.7-combat-loop.5` baseline. It is not deployed, restarted, registered, live accepted, or approved for construction. No game, desktop, production IPC, backup, credentials, or GitHub state was touched. Do not replace this JAR with any standalone feature-branch JAR: those each start from `.5` and would remove other integrated features.

## Merge decisions and cross-feature contracts

- `.6` adds combat classes and TerrainReader changes; boat adds separate classes, appends three read-only access transformers, and modifies ClientActionRequest/ClientActions/BridgeServer. Expedition merges its epoch/idle/observation/container hooks into those same files. All versions are explicitly `1.1.7-integrated.1`; no branch metadata overwrites another feature.
- One ClientActions active owner is checked before constructing either combat or boat. The action registry still rejects altered payload reuse and cannot start a second action while active. Draft coordination plans cannot enter the native action enum or the resident operation switch.
- Boat left/right controls stay within boat; ordinary paths preserve their previous suppression. Expedition guard applies to follow_path/break_block/place_block/combat_entity, not boat_drive. Global epoch sampling remains active during boat travel; later land tasks must re-observe and rebind when required.
- A large idle or active position discontinuity increments the epoch. Old queued land actions with no binding or stale epoch fail closed. Fresh admission after an event requires three stable loaded/supported grounded samples, exact current epoch, and origin within 0.25 blocks. Existing ordinary behavior remains compatible before a discontinuity unless the caller supplies an explicit binding. Never attach fresh epoch/origin to an old planned route merely to get it accepted.
- Combat action bodies retain navigation fields; the resident preserves them rather than dropping or silently rebasing them. The MCP validates a paired epoch/origin when supplied. Unknown/stale map observations do not establish safe corridors.
- Death, GUI, deadline, cancellation, player/world changes, disconnect and direct API takeover still flow through cleanup. `input_release_confirmed` and boat `input_released` are cleanup observations. `boat_settled` is separate; cancel does not freeze momentum or keep braking after ownership ends.
- Integration hardening: supplied expected_player_uuid is checked for every native action, and optional expected_action_session on cancel is checked atomically on the client thread. The new MCP always supplies it. Old HTTP/resident cancel callers keep the old optional behavior; this is not a claim of a global fenced executor.
- MCP errors or malformed results never cause automatic replays or release/takeover side effects. A possibly sent POST is reported conservatively as unknown. Status can only inspect the same explicit ID/session; caller reconciliation is required. Mutation input isolation remains enforced.

## Acceptance order for the sole authorized game executor

No commands in this document were run against a game. A future owner must verify deployment identity and preserve a rollback before any live trial, according to the user's current authorization.

1. Single-monster and safety gates first: one explicitly allowed target in an observed safe area; target/world/player/session mismatch; GUI/cancel/deadline/API takeover/death/disconnect; confirmed cleanup; no attacker action after terminal result. Check lost responses without issuing fresh IDs. Confirm ordinary walking/input regressions including the known sprint/physical-key limitations rather than assuming fixes.
2. Only after the first gate passes: a known loaded flat path around a simple obstacle, then mixed/unknown threat and creeper sweep refusal, health gates, blocked route, residual-risk/withdrawal termination. Do not label multi-monster farming as implemented.
3. Then a bounded water trial while already in the ordinary boat driver seat: straight route, turn, intermediate continuity, endpoint settling, cancel while moving, passenger/vehicle/world changes, unknown/narrow water, blocks/entities and deadline. Observe both input release and residual movement. No mounting or streamed continuation claim.
4. Later, only in the user's requested post-dragon stage: position changes while active and idle, stale queued actions, new bindings, dimension/player changes, container identity, and separately authorized future End capabilities. Offline pearl/box helpers alone do not authorize or enable native actions.
5. Construction remains gated on completion of all requested optimizations and applicable acceptance. This offline integration candidate does not satisfy that gate, and the new ranged/damage prototype is outside this frozen integration scope.

## Reproducibility and rollback

The delivery includes a full source archive, sources JAR, one integrated runtime JAR, diff from `.5`, explicit source hashes, original branch hashes, conflict decisions, offline regression logs/XML, independent review record, and the original `.5` runtime in a separate rollback directory. That rollback JAR is byte-identical to the verified baseline; no installer runs automatically. Restoring it later is a deployment action for the sole authorized executor, not part of this candidate build.

Offline test commands and machine-readable totals are in verification. Python discovery is per component to avoid importing a suite twice; the current union totals are parsed from actual logs, never obtained by adding branch totals. The single inherited watchdog skip refers to an unavailable frozen historical comparison source. The separate Windows-specific MCP launch/registration test and all game tests are explicitly unrun.
